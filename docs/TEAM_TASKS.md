# 时宜 ShiYi · 四人任务分工 V0.1

> 本文是按模块与依赖关系做出的**暂定分工**。四位成员简称：`xu` / `wu` / `lan` / `fu`。由于目前没有四位成员的 GitHub 用户名及技术专长，Issue 先在标题和正文中写责任人，不设置 GitHub Assignee。确认后可调整。

## 1. 统一开发目标

第一个可交付的 MVP 不是“完整养生平台”，而是完整运行以下路径：

**Android 查看节气卡 →（穿戴数据或主动反馈）了解状态 → 获取 2–3 项可选活动 → 用户选择 → Stack-chan 进行表情/语音引导 → 用户确认完成/拒绝 → App 反馈并更新推荐。**

中医药文化知识库作为这条路径的可靠内容层；Jev 先做可替换实验模块，不阻塞主流程；Stack-chan 不替代智能穿戴设备。

## 4. 三个交付关口（按依赖，不是官方截止日期）

**G0 · 并行开工**
- xu：API 契约 + 活动状态机草案 + 开发环境。
- wu：可编译 App + 四大页面 UI + 假数据状态标记。
- lan：设备型号、固件 SDK、屏幕/动作基础测试。
- fu：优先审核 12–20 张高质量内容卡，形成结构化 Schema。
- **关口验收：** 四人都各自有一个可 Review 的 PR；依赖未确定之处明确说明。

**G1 · 第一条完整闭环**
- xu：会话状态 + 本地持久化与联调 API。
- wu：App 推荐/选择/反馈连 API。
- lan：先模拟器，后以真机逐项替换。
- fu：规则推荐的候选活动与内容卡可被 API 调用。
- **关口验收：** 用户能在 App 发起一次活动并看到反馈（先允许机器人模拟器）。

**G2 · 比赛版本**
- 穿戴真实数据、机器人真机、知识问答与可重复 Demo。
- Jev 属于加分实验，在规则基线稳定后再上；不能阻塞主流程。
- **关口验收：** 真实数据可追溯、失败有回退、至少一次端到端演示和基础用户体验评测。

## 5. 关键依赖和交接

1. **xu → wu/lan/fu**：先冻结活动接口字段、任务状态与设备事件（推荐、选定、开始、完成、跳过、反馈）；变更必须 PR 讨论。
2. **lan → xu**：首先交付硬件能力表，再敲定设备通信方式。网络/音频方案不可凭型号假定。
3. **wu → xu/fu**：提交健康数据采集权限与真实设备结果；如不可获取，使用明确标注的演示数据，绝不伪造真实观察。
4. **fu → xu/wu**：交付内容 Schema、带来源的内容卡和候选活动标签，知识安全规则先于 LLM 上线。
5. **四人共同**：首次 Demo 联调每个模块负责人到场；用户研究与测试不由 fu 一人包办。

## 6. Git 与 PR 规则

- 分支：`feat/xu-session-api`、`feat/wu-season-ui`、`feat/lan-stackchan-control`、`feat/fu-knowledge-cards`。
- 每个 Issue 关联一个或数个 PR，PR 标注工作包编号、验收方式与截图/日志。
- `main` 是稳定集成分支，禁止强推；推荐至少一位非作者 Review，接口变更需对应调用方同意。
- 每周一次 20–30 分钟集成回顾，每次先看实际可运行功能与阻塞项，再调整计划。
- 没有完成实测的项目应标注 **模拟/待验证**；个人健康数据、API Key 与机器人配对密钥严禁提交。
