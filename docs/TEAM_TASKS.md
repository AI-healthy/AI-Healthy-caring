# 时宜 ShiYi · 四人任务分工 V0.2

> 本文是按模块与依赖关系做出的**暂定分工**。四位成员简称：`xu` / `wu` / `lan` / `fu`。由于目前没有四位成员的 GitHub 用户名及技术专长，Issue 先在标题和正文中写责任人，不设置 GitHub Assignee。确认后可调整。

## 1. 统一开发目标

第一个可交付的 MVP 不是“完整养生平台”，而是完整运行以下路径：

**Android 查看节气卡 →（穿戴数据或主动反馈）了解状态 → 获取 2–3 项可选活动 → 用户选择 → Stack-chan 进行表情/语音引导 → 用户确认完成/拒绝 → App 反馈并更新推荐。**

**健康建议以可追溯的现代循证研究和适用条件为依据**；节气、四时与中医药文化作为有意义的情境和兴趣体验增量，不能直接替代医学证据。传统健康实践如有针对具体人群和结局的可信研究，可在相同证据标准下评估。Jev 仅作为 P2 可替换实验，不阻塞主流程；Stack-chan 不替代智能穿戴设备。

## 4. fu 专项任务交付与证据边界（V0.2）

**FU-01 · 双层知识库与审核**
- **健康内容层**：睡眠、运动、压力管理等低风险生活方式建议；符合适用人群和研究证据的传统健康实践可纳入候选，不因传统来源直接肯定或否定有效性。
- **四时文化层**：节气习俗、文化与历史知识、季节性活动主题、兴趣探索。节气日期不能直接用于诊断或推断健康风险；涉及过敏、高温、日照等季节因素，应参考真实环境数据和用户反馈。
- **首批交付**：20 张可检索内容卡及 Schema；涉及健康主张的卡片包含 `content_id`、`content_type`、`source`、`target_population`、`evidence_summary`、`limitations`、`contraindications_or_cautions`、`review_status`，并记录查阅/更新日期；文化卡必须明确标注非医疗结论。证据强度说明评估方法，不将自定义标签误称为正式医学评级。
- **红线**：不能把四时或阴阳理论与穿戴生理数据建立未经验证的诊断映射；不由通用 Agent 自动提供处方、诊断或替代专业医疗建议。

**FU-02 · RAG 与结构化活动候选**
- 从知识库检索**可核验来源**，过滤无来源、超出适用条件或有明显风险的健康主张；来源不足时说明不确定性或不推荐。
- 向 xu 交付候选活动、证据 ID、适用条件、限制、节气主题等**结构化数据契约草案**，最终字段与 `packages/contracts/`、OpenAPI 由 xu 共同评审冻结。
- fu 提供内容召回、筛选与候选；**xu 的 Harness** 保留情境判断、记忆、主动触发、用户确认与最终执行责任，避免再造平行 Agent。
- 以静态规则/白名单为基础回退；RAG 不得编造文献或治疗结论。Jev 的模型对比作为 **P2 独立研究**，不成为首个 MVP 的阻塞条件。

**FU-03 · 用户研究与可证伪评测**
- 先针对真实大学生生活场景开展知情同意的访谈与观察，产出访谈提纲、去标识化发现、核心用户需求与方案修订记录。
- 设计可执行的两类对照：① 静态推荐 vs 用户偏好/历史反馈个性化推荐；② **相同健康活动**的普通展示 vs 四时文化主题展示（尽量控制内容与强度相同）。
- 预先记录接受率、活动完成率、打扰感、主观愉悦/放松体验，以及缺失数据和样本局限；区分产品体验改善与临床健康效果，不把合成 Benchmark 当真实人群效果。
- 用户数据遵循最小化与撤销/删除授权规则；未经同意不采集真实健康资料。

**交付形式**：fu 在 `content/`、`experiments/` 和经协商的 `services/api/` 目录提交内容、可运行代码、测试与实验方法文档；每项交付经至少一位队友 Review 并可复现。

## 5. 三个交付关口（按依赖，不是官方截止日期）

**G0 · 并行开工**
- xu：API 契约 + 活动状态机草案 + 开发环境。
- wu：可编译 App + 四大页面 UI + 假数据状态标记。
- lan：设备型号、固件 SDK、屏幕/动作基础测试。
- fu：产出双层知识分类与证据审核规范；交付首批 20 张可追溯内容卡与 Schema，并提供访谈提纲。
- **关口验收：** 四人都各自有一个可 Review 的 PR；依赖未确定之处明确说明。

**G1 · 第一条完整闭环**
- xu：会话状态 + 本地持久化与联调 API。
- wu：App 推荐/选择/反馈连 API。
- lan：先模拟器，后以真机逐项替换。
- fu：证据约束 RAG、白名单回退与时令情境候选活动可以通过约定接口供 Harness 使用，并标明来源/适用条件。
- **关口验收：** 用户能在 App 发起一次活动并看到反馈（先允许机器人模拟器）。

**G2 · 比赛版本**
- 穿戴真实数据、机器人真机、可溯源知识问答与可重复 Demo；收集经同意的访谈及试用反馈。
- FU-03 输出静态/个性化与普通/四时主题的对照方案及指标；样本不足时明确报告限制。
- Jev 是 P2 可选实验，仅在安全规则与基础闭环稳定后考虑，不阻塞主流程。
- **关口验收：** 真实数据可追溯、失败有回退、至少一次端到端演示和基础用户体验评测。

## 6. 关键依赖和交接

1. **xu → wu/lan/fu**：先冻结活动接口字段、任务状态与设备事件（推荐、选定、开始、完成、跳过、反馈）；变更必须 PR 讨论。
2. **lan → xu**：首先交付硬件能力表，再敲定设备通信方式。网络/音频方案不可凭型号假定。
3. **wu → xu/fu**：提交健康数据采集权限与真实设备结果；如不可获取，使用明确标注的演示数据，绝不伪造真实观察。
4. **fu → xu/wu**：交付证据分层的内容 Schema、来源/适用条件/风险信息、结构化候选活动及访谈/评价指标；xu 负责 Harness 接口、触发与安全规则落地，wu 负责在 App 中真实展示数据来源和用户反馈入口。
5. **四人共同**：首次 Demo 联调每个模块负责人到场；用户研究与测试不由 fu 一人包办。

## 7. Git 与 PR 规则

- 分支：`feat/xu-session-api`、`feat/wu-season-ui`、`feat/lan-stackchan-control`、`feat/fu-evidence-rag`。
- 每个 Issue 关联一个或数个 PR，PR 标注工作包编号、验收方式与截图/日志。
- `main` 是稳定集成分支，禁止强推；推荐至少一位非作者 Review，接口变更需对应调用方同意。
- 每周一次 20–30 分钟集成回顾，每次先看实际可运行功能与阻塞项，再调整计划。
- 没有完成实测的项目应标注 **模拟/待验证**；个人健康数据、API Key 与机器人配对密钥严禁提交。
